# M1/C 主菜单与进出局工作流

[游戏策划案](../游戏策划案.md)第 2.1 节定义整局如何开始，第 11 节定义局内反馈，第 13 节要求先用普通画面打通功能。M1 的本地入口直接进灰盒战场，模式、阵营和地图使用 M1 测试配置。新一局从首轮部署和会话初值开始，继续本局时保留现有状态。画面使用清晰的中文文本、可见的焦点和灰盒占位。

## 开工顺序

| 阶段 | 开工条件 | 计划 |
| --- | --- | --- |
| C1 启动菜单 | A1 已合入 | [C1 计划](C1-plan.md) |
| C2 开始进局 | C1、B1 均已合入 | [C2 计划](C2-plan.md) |
| C3 独立退出 | C1 已合入，可与 C2 并行 | [C3 计划](C3-plan.md) |
| C4 返回与重开 | C2、E2 均已合入。E2 已依赖 B2、D1、E1 | [C4 计划](C4-plan.md) |

## 每阶段交付

1. 开发前确认计划、前置 Issue 和远端 `main`。从更新后的 `origin/main` 建该阶段的 `codex/m1-cN` 分支。保留工作区已有本地修改，使用 UE5 MCP 制作或检查资产并验证编辑器内行为，按需正常编译 C++。
2. 按阶段计划实施，编译并运行各自的验收场景。记录使用的提交或工作区 diff、UE 版本、入口、操作步骤、实际结果和必要的日志或截图。
3. 实施结束后，为该阶段启动一个未参与实现的独立验收子代理。把计划、Issue、改动范围和可复跑步骤交给子代理，由它检查实现并独立重跑可运行场景。单一 UE 编辑器会话由验收者独占操作。验收者返回「通过」「失败」或「受阻」，逐项记录实际观察、证据路径和未验证项。修复失败项后由验收者复验。未运行的用例保持待验证。
4. 通过后使用指向 `main` 的独立 PR 交付该阶段，附子代理验收记录。C2 与 C3 合入后，I1 可提前验证 Win64 Development 包的地图烘焙和独立进程。C1 至 C4 都通过后，在父项 #4 汇总四个交付链接及可复现的测试记录或构建链接。
